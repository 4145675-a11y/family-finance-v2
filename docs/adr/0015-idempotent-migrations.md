# ADR-0015: כל migration ניתן להרצה חוזרת

- **Status**: Accepted
- **Date**: 2026-08-16
- **Milestone**: 2
- **Requirement IDs**: `SEC-RLS-001`

## הקשר

ההחלה הידנית הראשונה של Milestone 2 נכשלה:

```
ERROR: 42710: trigger "profiles_touch_updated_at" for relation "profiles" already exists
```

השגיאה דיווחה על טריגר של `profiles` בזמן שהמשתמש הריץ, לכאורה, את קובץ ההזמנות. הסיבה התבררה מספירת שורות: הקובץ שהודבק הגיע לשורה 283, בעוד קובץ ההזמנות מונה 139 שורות. `143 + 139 + 1` — בדיוק 283. חלון ה־SQL Editor עדיין החזיק את המיגרציה השנייה, וההזמנות הודבקו מתחתיה.

השגיאה עצמה נכונה. מה שהיה שגוי הוא שהיא לא ניתנת לפענוח: היא מצביעה על אובייקט מקובץ אחר, ואינה רומזת שהבעיה היא הרצה כפולה.

**הפער האמיתי**: המיגרציות לא היו ניתנות להרצה חוזרת. `create table` ו־`create index` נכתבו עם `if not exists`, אבל 7 טריגרים, 12 policies ו־enum אחד — לא. PostgreSQL אינו מציע `IF NOT EXISTS` עבורם.

`08-TEST-PLAN.md` דורש בדיקת migration "על DB נקי ועל snapshot קיים רלוונטי" ואסטרטגיית recovery. מיגרציה שנשברת בהרצה שנייה נכשלת בשתי הדרישות.

## החלטה

כל אובייקט במיגרציה נוצר בצורה שניתן להריץ שוב:

| אובייקט | דפוס |
|---|---|
| table, index, extension, schema | `if not exists` (נתמך) |
| function | `create or replace` |
| **trigger** | `drop trigger if exists … on …;` ואז `create trigger` |
| **policy** | `drop policy if exists … on …;` ואז `create policy` |
| **type / enum** | בלוק `do $$ … if not exists (select 1 from pg_type …) … $$` |

הטיפול ב־enum שונה בכוונה: הפלה ויצירה מחדש של טיפוס שעמודה תלויה בו הייתה מפילה את העמודה. בדיקת קיום היא הדרך הבטוחה היחידה.

הפלה ויצירה מחדש של טריגר או policy בטוחה: היא מחליפה הגדרה, לא נתונים. בתוך הטרנזקציה המשתמעת של המיגרציה אין חלון שבו הטבלה חשופה — אם ההרצה נכשלת, הכול חוזר לאחור.

## אכיפה

`tools/migrations.test.mjs` — 25 בדיקות:

- לכל `create trigger` יש `drop trigger if exists` **שקודם לו** בקובץ.
- לכל `create policy` יש `drop policy if exists` מקביל.
- אין `create type` חשוף; ה־enum עטוף בבדיקת קיום מול `pg_type`.
- אין `create table`/`create index` בלי `if not exists`, ואין `create function` בלי `or replace`.
- **אף אובייקט אינו מוגדר בשני קבצים** — הכשל הזה היה מייצר בדיוק את אותה שגיאה מבלבלת.
- `profiles_touch_updated_at`, האובייקט שנכשל בפועל, שייך לקובץ אחד ויחיד.
- בדיקת שפיות שמוודאת שה־regex אכן תפס את כל הטריגרים, כדי שהחבילה לא תעבור על ריק.

אומת שלילית: הסרת ה־`drop` של `profiles_touch_updated_at` הפילה שתי בדיקות עם הודעה שמסבירה את התיקון. הקובץ שוחזר ואומת.

## מה זה לא פותר

הרצה חוזרת בטוחה **אינה** מנגנון גרסאות. אין כאן טבלת ledger שיודעת אילו מיגרציות הוחלו; הסדר עדיין ידני. כשתתווסף שרשרת CI מול מסד — או Supabase CLI עם היסטוריית מיגרציות — נשקול ledger, וזה יהיה ADR נפרד.

## השלכות

- חיוביות: הרצה כפולה, הדבקה חלקית או retry אינם משאירים מצב שבור. אפשר להריץ קובץ שוב כדי לוודא שהוא הוחל.
- שליליות: רעש קל בקבצים — שורת drop לפני כל trigger ו־policy. מחיר סביר.
- על המיגרציות שכבר הוחלו: הרצה חוזרת של הקבצים המעודכנים בטוחה ומייצרת סכימה זהה.

## תנאי ביטול

מעבר לכלי מיגרציות עם ledger משלו עשוי לייתר חלק מהדפוסים. הבדיקה תתעדכן, לא תימחק.
