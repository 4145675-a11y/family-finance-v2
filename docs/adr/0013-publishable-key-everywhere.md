# ADR-0013: publishable key בלקוח ובשרת; אין service role בשום מסלול בקשה

- **Status**: Accepted
- **Date**: 2026-08-16
- **Milestone**: 2
- **Requirement IDs**: `SEC-KEY-001`, `SEC-RLS-001`

## הקשר

Supabase החליף את מודל המפתחות הישן (`anon` JWT + `service_role` JWT) בזוג חדש: **publishable key** (`sb_publishable_…`) ל־client, ו־**secret key** (`sb_secret_…`) לשרת. הפרויקט קיבל publishable key בלבד, וזו הנחיה מפורשת מהמשתמש.

השאלה האמיתית ב־Milestone 2 אינה איזה מפתח בלקוח — היא **באיזה מפתח משתמש קוד השרת**. הדפוס הנפוץ ב־Next.js הוא לתת לשרת מפתח שעוקף RLS "כי הוא צד שרת ולכן אמין".

## החלטה

1. **הלקוח** משתמש ב־publishable key. (`apps/web/lib/supabase/client.ts`)
2. **השרת משתמש באותו publishable key**, יחד עם ה־session של המשתמש מה־cookie. (`apps/web/lib/supabase/server.ts`)
3. **אין secret key ואין service role בשום מקום בקוד** — לא בלקוח, לא בשרת, לא ב־CI.
4. `apps/web/lib/env.ts` **דוחה** מפתח שאינו מתחיל ב־`sb_publishable_`, ובכלל זה anon JWT ישן ו־secret key.
5. חזרה ל־legacy anon key מחייבת ADR חדש עם סיבה מוכחת.

## למה גם השרת כפוף ל־RLS

זו ההחלטה המהותית, ולא רק בחירת מפתח.

מפתח שעוקף RLS הופך כל באג בשרת לפרצת בידוד. `where household_id = $1` שנשכח, פרמטר שמגיע מהמשתמש בלי בדיקה, join שגוי — כל אחד מהם מדליף נתונים בין משפחות. כשהשרת פועל תחת ה־session של המשתמש, אותו באג פשוט מחזיר אפס שורות: המדיניות במסד תופסת אותו.

`07-SECURITY-PRIVACY.md` קובע "UI אינו גבול אבטחה". המסקנה הנגזרת היא שגם השרת אינו הגבול — **המסד הוא הגבול**, ולכן כל מסלול בקשה עובר דרכו ככפוף למדיניות.

מה שבאמת ידרוש מפתח מוגבר בעתיד (עבודות רקע, retention, webhooks) יגיע ב־milestone שמגדיר אותן, מאחורי גבול מפורש, ולא כברירת מחדל של כל בקשה.

## אכיפה

| שכבה | מנגנון |
|---|---|
| חוזה סביבה | `readPublicEnv()` דוחה כל מפתח שאינו publishable; הודעת השגיאה אינה מהדהדת את הערך |
| מקור | `tools/check-client-secrets.mjs` — מודול שנגיש ללקוח לא יזכיר מזהה סוד |
| bundle | אותו שער סורק את `.next/static` הבנוי אחר ערכים בצורת סוד |
| בדיקות | 7 בדיקות ב־`env.test.ts`, כולל דחיית anon JWT ודחיית secret key |

אומת שלילית: הפניה מושתלת ל־`SUPABASE_SERVICE_ROLE_KEY` במודול לקוח הפילה את השער (exit 1); אותה הפניה מאחורי `import 'server-only'` עברה — כלומר השער מבחין נכון ואינו סתם מחפש מחרוזת.

## השלכות

- חיוביות: אין נכס במאגר שעוקף RLS; באג בשרת אינו הופך לדליפה בין־משפחתית; שכבה אחת של אמת להרשאות.
- שליליות: פעולות שבאמת דורשות הרשאה מוגברת יצטרכו תכנון מפורש. זו התוצאה הרצויה.
- ה־publishable key מגיע לדפדפן ואינו סוד. הוא מזהה פרויקט; בלי session הוא אינו פותח דבר, כי אין policy שמתירה ל־`anon`.

## תנאי ביטול

צורך מוכח בעבודת רקע ללא session. תידרש הפרדה מפורשת: מודול server-only, לא ב־request path, עם ADR ובדיקות ייעודיות.
